# 互连（Interconnect）

互连是一个面向 SimpleBus（见 [bus](bus_zh.md)）的多主设备、多从设备交叉开关（crossbar）。它将 `numMasters` 个主设备端口连接到 `slaveAddrMap` 中每个从设备各自的一个端口，并对访问同一从设备的多个主设备进行仲裁。实现在 `src/main/scala/bus/Interconnect.scala` 中。

## 参数

| 参数 | 类型 | 说明 |
|----------------|-------------------------------|-------------|
| `numMasters` | `Int` | 主设备端口数量。 |
| `slaveAddrMap` | `Seq[(UInt, (Int, Int))]` | 每个从设备一项，见下文。 |

### `slaveAddrMap`

按从设备索引顺序，每个从设备一项：

```scala
Seq(
  (base0, (hi0, lo0)),
  (base1, (hi1, lo1)),
  ...
)
```

每一项是一对：

- **`base: UInt`** — 从设备的基地址（32 位）。
- **`(hi, lo)`** — 用于地址译码的 `addr` 的闭区间位范围。

当 `addr(hi, lo)` 等于从设备 `s` 基地址的高几位（即 `base >> lo`）时，请求就定位到从设备 `s`。每个从设备的译码范围按其自身大小选取：译码位数 `hi - lo + 1` 应与该从设备的可寻址跨度相匹配，而所有低于 `lo` 的地址位则原样直通给从设备。例如，一个映射在基地址 `0x8000_0000`、其区域可由 `addr[31:28]` 选中的从设备，其条目为 `(0x8000_0000.U, (31, 28))`；任何最高半字节为 `0x8` 的请求都会被路由到它，而与其低 28 位无关。

各条目的译码范围不得重叠，因为每个能译码出该请求的从设备都会看到自己的 `reqValid` 被置起，重叠的条目会产生未定义行为。

## 端口

| 端口 | 类型 | 说明 |
|---------|------------------------------|-------------|
| `masters` | `Vec(numMasters, DataInterface)` | 主设备端口，索引 0 优先级最高。 |
| `slaves` | `Vec(numSlaves, Flipped(DataInterface))` | 与 `slaveAddrMap` 中的条目一一对应，顺序相同。 |

增加主设备是可行的，但不建议超过少数几个：译码、仲裁和响应 mux 都按 `masters × slaves` 的规模增长，并且 grant/响应逻辑会在所有通道之间形成一条很长的组合路径。

## 地址译码

每个请求在 `reqValid` 触发时被捕获到每个主设备各自的寄存器（`reqBuffer`）中。一个周期后，`slaveSel(m)(s)` 将缓存的地址位 `addr(hi, lo)` 与地址映射表中每个从设备的基地址进行比较。因此译码操作的是*已寄存*的请求，并在请求到达后的下一个周期有效。

## 仲裁

仲裁采用**固定优先级，主设备 0 优先级最高**。通道 `(m, s)` 在满足以下条件时被授予（grant）：

- 从设备 `s` 不忙；
- 主设备 `m` 有一个选择了从设备 `s` 的待处理请求；
- 没有更高优先级的主设备（索引 `< m`）也在选择从设备 `s`。

两个记账位向量实现了这一逻辑：

- `pendingBits(m)` — 当主设备 `m` 收到请求时置位，当其任一通道被授予时清零。
- `busyBits(s)` — 当任一被授予的主设备以从设备 `s` 为目标时置位，在该从设备 `respValid` 时清零。每个从设备同一时刻只有一个在途事务。

## 响应路由

`respMuxBits(m)(s)` 在 `(m, s)` 被授予时打开响应通道，并在从设备 `s` 置起 `respValid` 时关闭。每个主设备的 `respValid` 和 `rdata` 是对其所有打开通道的 `Mux1H`。

从设备侧的转发：从设备看到的 `reqValid` 是所有 `channelSel(m)(s)` 的或（OR），而 `addr`、`size`、`wen`、`wdata` 和 `wmask` 则从被授予的主设备的 `reqBuffer` 中 mux 而来。

## 时序

- 请求在到达后**至少一个周期**才被转发到被选中的从设备。
- 响应通道在请求到达后**至少两个周期**才打开。
- 每个主设备最多有一个未完成的请求；每个从设备一次只处理一个事务。

## 缓冲与组合路径

互连的设计目标是少量主设备和少量从设备，其中从设备通常是几个存储器和几个用于 MMIO 的交叉开关（见 [crossbar](crossbar_zh.md)）。这两类从设备都会缓冲自己的响应。互连有意**不对响应进行缓冲**：它的延迟至关重要，因为每条指令取指都要经过它；而且只有少量从设备时，响应 mux 逻辑的深度不足以需要流水化。

另一方面，互连和交叉开关都设置了请求缓冲，原因相同：在 CPU 一侧，生成地址本身就可能已经是一条很长的组合路径，如果再把它馈入扇出很大的从设备选择译码，就会关键性地延长这条路径。对请求进行缓冲切断了这条路径。

细节：

- 每个主设备端口都有一个完整的请求缓冲（`reqValid` 加所有载荷字段都经过寄存），因此主设备看到的只是一个寄存器输入，CPU 侧的地址生成路径也终止于寄存器。
- 从设备的载荷输入来自对各个主设备缓冲的 mux，而不是直接来自主设备。
- grant 链（`channelSel`）组合了译码、忙碌、待处理以及更高优先级主设备的检查；响应 mux 在其之上又增加了一级 `Mux1H`。两者的规模都随 `numMasters` 增长，是增加主设备时的主要时序顾虑。
- 响应输出由**已寄存**的 mux 位（`respMuxBits`）选择，而不是由当前译码组合得出。由于请求经过缓冲，从设备的响应最早在请求到达互连后两个周期到达——一个周期进入缓冲，一个周期转发——这恰好留下足够的周期，在响应必须被路由回去之前把 mux 选择寄存下来。
